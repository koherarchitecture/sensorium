# V0.1.3-AMD64-RECONCILE — create v0.1.3 branch, commit source, commit artefacts, push source

For the Claude Code session running on the **x86_64 Linux dev box** (`uname -m` = `x86_64`). The v0.1.3 amd64 `.deb` and `.flatpak` are already built and staged in `releases/linux-amd64/`; the sandboxed-flatpak smoke test passed on 21 May 2026 afternoon. This runbook reconciles git history so the Mac and arm64 sessions can take a clean source baseline.

**This file SUPERSEDES `releases/V0.1.3-AMD64-BUILD.md`.** That file assumed the build was still pending; in fact the build is complete and only the commit/push reconcile remains. Ignore `V0.1.3-AMD64-BUILD.md` from this point on.

## Why a reconcile is needed (21 May 2026 evening, Mac dev box discovery)

The Mac sat down to run `V0.1.3-MAC-BUILD.md` and found that `origin/v0.1.3` does not exist — neither locally nor on `github.com/koherarchitecture/sensorium`. The 21 May amd64 work landed entirely in the working tree (modified files + untracked artefacts) without ever committing or branching. The MAC and ARM64 build runbooks both do `git fetch origin && git checkout v0.1.3 && git reset --hard origin/v0.1.3` as step 2; without `origin/v0.1.3`, that block fails. This runbook fixes that on the amd64 box where the source changes actually live.

The release-artefact push discipline (`tools-scratch/CLAUDE.md`, binding 9 May 2026) requires source commits and artefact commits to be separable so that source pushes freely while artefacts wait for an explicit "release" instruction. So this runbook produces two commits on the v0.1.3 branch: a source commit (pushable), then an amd64-artefact commit on top of it (local-only).

## Expected state on this host before starting

- `uname -s -m` = `Linux x86_64`.
- Branch: `v0.1.2`. No local `v0.1.3` branch yet. `origin/v0.1.3` does not exist.
- Modified files (uncommitted v0.1.3 substance — full list in step 5).
- Untracked files: the three `V0.1.3-*-BUILD.md` runbooks, this `V0.1.3-AMD64-RECONCILE.md`, the two new Rust + JS modules (`tone_suggestions.rs`, `tone-suggestions.js`), and the two amd64 artefacts in `releases/linux-amd64/`.
- Last commit: `b297c6f release(linux-arm64): sensorium 0.1.2 arm64 .deb + arm64 .flatpak (build-only, local-only, not released)`.

If any of the above is materially different, stop and report — the Dropbox sync may have drifted, or another host may have already committed.

#   .deb SHA-256 = ec28ecc8614e00b119075e9f97d891bcc6d551fa0aed194f1d400e96709158a9

# 5. Stage source + runbook + new modules with explicit paths. Do NOT use `git add -A` or `git add .`.
#    This keeps the source commit and the artefact commit cleanly separated.

# 6. Commit the source. Pushable per release-artefact push discipline.
git commit -m "$(cat <<'EOF'
v0.1.3 source: calibration-load fixes + suggested-tone cues + install-flavour notice

Three calibration-load fixes — together resolve the "no flavour loaded" error
seen by users on freshly-installed v0.1.2 across all platforms.

- src-tauri/src/lib.rs: flavour seed-and-load moved into the .setup() callback
  with real paths via handle.path().resource_dir() and handle.path().app_config_dir().
  The startup-time call previously passed (None, None) and relied on the
  env!(CARGO_MANIFEST_DIR) fallback, which silently resolved to the build host's

  causing the error to surface only on user installs.
- src-tauri/src/flavour.rs: _up_/flavours/ checked first in both load_flavour
  and ensure_flavour_in_user_data. Tauri's bundler prefixes ../-relative
  resources with _up_/ for collision protection; the loader was looking at the
  plain flavours/ path only.
- packaging/flatpak/app.koher.sensorium.yml: explicit mkdir + cp of the bundled
  /usr/lib/sensorium tree from the extracted .deb into /app/lib/sensorium.
  The flatpak manifest was never copying this tree, so even after the
  flavour.rs fix the file did not exist inside the flatpak sandbox.

Defence-in-depth + UI polish:

- src/js/first-run.js: wizard-time seed call before Calibration.run().
  Re-attempts the flavour seed if the setup-time path silently fails for some
  user-specific edge state.
- src/js/settings-modal.js: three dead install-flavour buttons (From URL,

originally-planned 5 June v0.1.3 substance):

- src-tauri/src/rules/tone_suggestions.rs (new module): derive() reads the

  Demand specifics / Withdraw investment.

  iteration introduces click-to-insert; v0.1.3 does not read it.
- src-tauri/src/ipc.rs: stateless suggested_tones(fingerprint) IPC.
- src-tauri/src/lib.rs: handler registration.
- src/js/ipc.js: Tones.suggest wrapper.
- src/js/tone-suggestions.js (new module): non-interactive — cues are
  display-only, system-selected, bronze-on visual state, hidden when no
  triggers fire or no fingerprint exists (silence is itself a signal).
- src/index.html: composer markup + CSS for .tone-suggestions / .tone-cue.
- src/js/app.js + src/js/filter-panel.js: init wiring and dynamic-import
  call inside applyFingerprint.

- scripts/sync-koher-ui.sh: KOHER_ROOT depth corrected from 4-level
  (../../../../) to 2-level (../../) for the post-13-May tools-release/sensorium/
  path. Was failing silently with "source not found" until fixed.

src-tauri/tauri.conf.json, src-tauri/Cargo.toml. Sycophancy flavour version

## Auth fallback (only if step 7 fails)

If `git push -u origin v0.1.3` returns an auth error (HTTP 401 / "could not read Username" / "Permission denied (publickey)"), this host lacks GitHub auth. **Do not stop the runbook.** Continue with steps 8-9 to land the artefact commit locally. The Dropbox-synced `.git/` will carry both commits to the Mac, and the Mac (which has auth) can push the source commit afterwards with:

```bash
# On Mac, after Dropbox sync settles (~30 seconds):
cd ~/Dropbox/personal_projects/koher/tools-release/sensorium
git fetch . v0.1.3:v0.1.3 2>/dev/null || git branch v0.1.3 $(git log v0.1.3 --format=%H | sed -n '2p')
git push origin v0.1.3^:v0.1.3
# ^ pushes the source commit (parent of the artefact-commit HEAD), leaving the
#   artefact commit local-only on Mac too.
```

The `v0.1.3^` form names the source commit by its position (one parent of the artefact-commit HEAD). It avoids hand-typing SHAs.

## What NOT to do

- **Do not push the artefact commit.** Per the Release Artefact Push Discipline rule. Only the source commit goes to origin in this session. The full release (all 6 artefacts on a GitHub Release) happens later from the Mac after explicit user authorisation.
- **Do not `git add -A` or `git add .`** — the runbook stages files explicitly so the source commit and artefact commit are separable. A blanket add would mix them and force a follow-up `git reset` to split them.
- **Do not delete `V0.1.3-AMD64-BUILD.md`** — that file is referenced from `tools-scratch/02-sensorium/buffer.md` ("amd64 rebuild" task line). It is superseded in spirit (the rebuild already happened) but the file stays where it is. Future cleanup can fold it into the buffer-archive section.
- **Do not rebuild the artefacts.** They are already correct (per the 21 May smoke test). This runbook is reconcile-only.
- **Do not edit BUILD-STATUS.md from this session.** That file is the orchestrator's resume tracker; the Mac session updates it after Mac builds finish. This runbook only reports outcomes for the orchestrator to fold in.

## Failure modes

- **`git checkout -b v0.1.3` fails: "a branch named 'v0.1.3' already exists"** — some other host (or an earlier interrupted session) already created the branch. Run `git branch -v | grep v0.1.3` and inspect. If the existing branch has no commits beyond `b297c6f`, run `git checkout v0.1.3` to resume on it. If it has commits, stop and report — manual reconciliation needed.
- **`sha256sum` mismatch in step 3** — the staged `.deb` / `.flatpak` on disk are not the 21 May builds. Possible causes: Dropbox sync mid-update; an earlier rebuild that didn't get logged. Stop. Do not commit stale artefacts.
- **`git push` rejected because `origin/v0.1.3` already exists with different history** — another host pushed first. Run `git fetch origin v0.1.3 && git log origin/v0.1.3 -3 --oneline` and reconcile by hand. Do not force-push.
- **Permission errors writing into `.git/`** — Dropbox is holding a file open. Wait 30 seconds and retry. Persistent failures point at the known `.git/` corruption pattern; see `releases/RECOVERY.md` for the fresh-clone path.
