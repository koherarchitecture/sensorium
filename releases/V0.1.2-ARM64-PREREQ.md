## Why this exists

v0.1.2 closes the arm64-flatpak gap that v0.1.0 and v0.1.1 both deferred. The build script (`scripts/build-flatpak.sh`) is now arch-aware — on an arm64 host it produces an arm64 `.flatpak` automatically. But `flatpak-builder` needs the GNOME runtimes installed for the *host's* arch. The amd64 dev box already has them from the v0.1.0 build; the arm64 VM had them from an earlier session (confirmed 9 May). If a fresh arm64 host joins the matrix, this brief installs them.

## Steps

```bash
# 1. Confirm you are on the arm64 host. If `uname -m` returns something
#    other than `aarch64`, stop — this brief is wrong host.
uname -s -m

# 2. Recover and align with main. Per releases/RECOVERY.md.
cd /media/psf/Dropbox/personal_projects/koher/tools-scratch/02-sensorium/sensorium
pkill -f tauri 2>/dev/null
pkill -f flatpak-builder 2>/dev/null
rm -rf src-tauri/target/release dist .flatpak-builder
git fetch origin --force --prune
git reset --hard origin/main
git clean -fd
git config user.name "Koher Architecture"
git config user.email "hello@koher.app"

# 3. Switch to the v0.1.2 branch where the arm64 flatpak scaffolding lives.
git fetch origin
git checkout v0.1.2
git pull

# 4. One-time prereq: register flathub and install the arm64 GNOME
#    runtimes the flatpak build needs. `--user` keeps everything in the
#    user's home dir; no sudo needed.
flatpak remote-add --user --if-not-exists flathub https://flathub.org/repo/flathub.flatpakrepo
flatpak install --user flathub org.gnome.Platform//49 org.gnome.Sdk//49

# 5. Confirm the runtimes registered for arm64.
flatpak list --user --runtime
git status
git log -1 --oneline
```

## If something fails

- **`flatpak install` reports "no such ref" for arm64.** Flathub may not serve `//49` for arm64 from this VM's network. Try `//48` as a fallback (`flatpak install --user flathub org.gnome.Platform//48 org.gnome.Sdk//48`). Report which version actually installs so the manifest's `runtime-version` can be aligned.
- **`git checkout v0.1.2` fails.** Run `git fetch origin` then retry. If the branch genuinely doesn't exist remotely, the v0.1.2 work hasn't been pushed from Mac yet — stop and report.
- **Any `Could not read <sha>` errors during git operations.** That's the `.git/`-via-Dropbox corruption pattern. Re-run step 2 after a minute (Dropbox sync catching up). Persistent errors mean a fresh clone is needed — see `releases/RECOVERY.md` for that path.
