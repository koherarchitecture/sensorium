### Source state — what shipped in v0.1.3

Per the source commit message on `d835413`, v0.1.3 contains:

1. **`src-tauri/src/lib.rs`** — flavour seed-and-load moved into the `.setup()` callback with real paths via `handle.path().resource_dir()` and `handle.path().app_config_dir()`. Replaces the eager startup load that passed `None, None` and relied on dev/compile-time fallbacks that don't exist on user machines. Load-bearing fix for the "no flavour loaded" calibration error.
2. **`src-tauri/src/flavour.rs`** — `load_flavour` and `ensure_flavour_in_user_data` check `<bundle_resource_dir>/_up_/flavours/{slug}.json` first, falling back to plain `flavours/`. Tauri's bundler prefixes `../`-relative resources with `_up_/` for collision protection; the loader was only looking at the plain path. Discovered via the first smoke test of the first v0.1.3 amd64 flatpak.
3. **`packaging/flatpak/app.koher.sensorium.yml`** — `mkdir -p /app/lib && cp -r deb-payload/usr/lib/sensorium /app/lib/sensorium` line added after the binary install. The manifest had been extracting the .deb but never copying the `/usr/lib/sensorium/` tree to `/app/lib/`; the flatpak was shipping without any bundled resources at all. Bug present since the first flatpak build (v0.1.0); only visible because the lib.rs setup-callback fix was in place to log the failure. Discovered via the second smoke test.
4. **`src/js/first-run.js`** — defence-in-depth wizard-time seed before `Calibration.run()`. Re-attempts the seed if the setup-time path silently fails for any user-specific edge state.
5. **`src/js/settings-modal.js`** — three dead From URL / From file / Browse registry buttons wired to an inline notice. v0.1 does not implement user-installable flavours (Sycophancy ships bundled).
6. **`src-tauri/src/rules/tone_suggestions.rs` (new module)** + `src-tauri/src/schema.rs` (`ToneSuggestion` struct) + `src-tauri/src/ipc.rs` (stateless `suggested_tones(fingerprint) -> Vec<ToneSuggestion>` IPC) + `src-tauri/src/lib.rs` (handler registration) + `src/js/ipc.js` (`Tones.suggest` wrapper) + `src/js/tone-suggestions.js` (new module) + `src/js/app.js` + `src/js/filter-panel.js` + `src/index.html` (composer markup + CSS for `.tone-suggestions` / `.tone-cue`) — **suggested-tone cues above the composer**. 5-candidate vocabulary (Push harder / Stay flat / Disagree firmly / Demand specifics / Withdraw investment); up to 3 surfaced at a time based on fingerprint dial averages + folds ratio. **Non-interactive** — the system selects which cues appear; the user reads them as coaching and writes the next message in that register. Bronze-on visual state, hidden when no fingerprint exists or no triggers fire (silence is itself a signal). Per Prayas's 21 May direction: "no interaction — the buttons are selected by system." Original click-to-insert implementation was reverted before commit; the `ToneSuggestion.hint` field is retained in the Rust schema as inert metadata in case a later iteration restores it.
7. **`scripts/sync-koher-ui.sh`** — `KOHER_ROOT` relative depth corrected from `../../../../` (pre-13-May, 4-level) to `../../` (current `tools-release/sensorium/` 2-level). `beforeBuildCommand` runs this script on every build; was silently failing until fixed.

Version stamped to `0.1.3` across `package.json`, `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml`. Sycophancy flavour version unchanged (the flavour JSON itself did not change).

## Gotchas to watch for on the Mac side

- **Build-machine masking** — the Mac dev box's binary has `env!("CARGO_MANIFEST_DIR")` baked in at compile time pointing at `~/Dropbox/personal_projects/koher/tools-release/sensorium/src-tauri/`. That path exists on disk on the Mac. The compile-time-manifest fallback in `flavour::load_flavour` will silently succeed on the build Mac itself even if the lib.rs / flavour.rs / flatpak-manifest fixes are all broken, because path 4 inside `load_flavour` finds the source-tree's `flavours/sycophancy.json` directly on disk. Any smoke test of the freshly-built DMG on the Mac that produced it tells you nothing about whether the fix works on a user machine. The amd64 flatpak sandbox smoke test (already passed on the Linux box) is the cleanest verification we have.
- **Dropbox-synced `.git/`** — the Linux box's `.git/` is in the Dropbox-synced path. When the Mac picks up changes, the safest move is `git fetch origin v0.1.3` against GitHub rather than trusting the Dropbox-synced refs. If `git status` or `git log` ever returns "could not read sha" or similar object-corruption errors on the Mac, the fix is `git fetch --force --prune` (per the 9 May `releases/RECOVERY.md`).
- **Mac's local artefact commit** — if the Mac picks up the Linux box's artefact commit (`8f97789`) via Dropbox sync of the `.git/`, it will be on the Mac's `v0.1.3` branch but not on `origin/v0.1.3`. The Mac's own Mac-DMG artefact commit will stack on top of it. When time comes to release, the order of commits on the Mac's `v0.1.3` should be `d835413` (source, on origin) → `8f97789` (amd64 artefacts, local-only) → Mac-artefact-commit (local-only) → arm64-artefact-commit (local-only, also picked up via Dropbox from the VM). All four can coexist; the GitHub release tag `v0.1.3` points at `d835413` (the source commit), not at any artefact commit.
- **`.git-bak-myinit-1779366339/`** — backup folder from the Linux box's earlier mistaken `git init` attempt. It's a sibling of `.git/` in the sensorium folder. Should NOT affect anything (git ignores other `.git*` paths during status/add). If Prayas confirms it can be deleted, the Linux box can remove it; for now it sits on disk in case it ever needs inspection.
- **Suggested-tone cues are non-interactive** — if anyone looks at the cue pills and tries to click them expecting a hint to insert into the composer, that was the original design but got reverted per Prayas's direction 21 May. Final behaviour: display-only, system-selected. The `ToneSuggestion.hint` field in the Rust schema is inert metadata that nothing reads; safe to keep for forward compatibility if Dhyeya's iteration restores click-to-insert.
