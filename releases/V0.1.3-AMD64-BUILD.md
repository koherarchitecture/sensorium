# V0.1.3-AMD64-BUILD — build the amd64 .deb and amd64 .flatpak

For the Claude Code session running on the **x86_64 Linux dev box**. Builds the v0.1.3 amd64 artefacts and stages them in `releases/linux-amd64/`. **Build only — no release.** The artefacts sit ready for the v0.1.3 ship window (target the v0.1.3 release window (after smoke test passes)).

**Context for v0.1.3:** Hotfix release overriding the two-week cadence floor (v0.1.2 shipped 18 May). Three source fixes ship across all six artefacts: (a) `src-tauri/src/lib.rs` moves flavour seed-and-load into the setup callback with real paths via `handle.path()` — load-bearing fix that addresses the "no flavour loaded" calibration error on every installed build; (b) `src/js/first-run.js` adds defence-in-depth wizard-time seed; (c) `src/js/settings-modal.js` wires the three dead install-flavour buttons to an inline notice. The flatpak smoke test below is the **primary verification of the lib.rs fix for the whole 6-artefact release** — the flatpak sandbox blocks the host's source-tree from masking the compile-time-manifest fallback, so a clean wizard walk-through here proves the fix works on a user machine. Mac and arm64 builds verify by transitivity (lib.rs change is platform-independent).

## Smoke test — primary verification of the v0.1.3 lib.rs fix

⚠️ **This smoke test is load-bearing for the whole 6-artefact release**, not a nice-to-have. The flatpak sandbox is the cleanest available test that the lib.rs setup-time seed-and-load works on a user machine — the sandboxed binary cannot see the host's source-tree paths, so the compile-time-manifest fallback (path 4 inside `flavour::load_flavour`) cannot fire. Only the proper user-data + bundle-resource paths are available, which is exactly the user-machine condition. Mac and arm64 builds verify the same code path by transitivity (lib.rs change is platform-independent).

```bash
# Clear any prior install + user-data to force fresh first-run state.
flatpak uninstall --user app.koher.sensorium -y 2>/dev/null
rm -rf ~/.var/app/com.koher.sensorium/

# Install the freshly-built bundle.
flatpak install --user --bundle releases/linux-amd64/sensorium-0.1.3-amd64.flatpak -y

# Launch.
flatpak run app.koher.sensorium &
sleep 5

# Manual checklist (walk the wizard end-to-end):
#   [ ] Step 1: enter dummy OpenRouter key, confirm storage step succeeds.
#   [ ] Step 2: Ollama detection runs (may show "daemon not detected" — OK,
#       click SKIP to proceed since the v0.1.3 fix is about flavour loading,
#       not Ollama).
#   [ ] Step 3 (CRITICAL): calibration step. Confirm it DOES NOT show
#       "Calibration failed: no flavour loaded — install a flavour config first."
#       If the wizard reaches "Calibration complete." the lib.rs fix is verified.
#   [ ] Open Settings (gear icon). Scroll to Flavour section.
#   [ ] Click "From URL…" — inline notice should appear in accent colour.
#   [ ] Click "From file…" — same notice should appear (idempotent).
#   [ ] Click "Browse registry…" — same notice.
#   [ ] Close Settings, close window.

pkill -f sensorium 2>/dev/null
flatpak uninstall --user app.koher.sensorium -y
```

If calibration completes cleanly and the three install-flavour buttons show the inline notice, the v0.1.3 release is verified — Mac and arm64 builds inherit the verification by code-path transitivity. If calibration shows the "no flavour loaded" error, the lib.rs fix did not carry over correctly into the binary — stop and report; do not stage the build for release.

## Failure modes

- **`./node_modules/.bin/tauri: not found` after npm install** — the cli-linux-x64 binding didn't install. Inspect with `ls node_modules/@tauri-apps/`. If only `cli-darwin-*` is there, npm's optional-dependencies bug bit again — rerun `rm -rf node_modules package-lock.json && npm install`.
- **`bash scripts/build-flatpak.sh` fails on a missing runtime** — re-confirm `flatpak list --user --runtime` shows both `org.gnome.Platform//49` and `org.gnome.Sdk//49` for amd64.
- **flatpak-builder stalls** — typical fix is `rm -rf .flatpak-builder dist/flatpak-build dist/flatpak-repo` and retry. The script's `--force-clean` should handle most cases, but a stale OSTree repo can confuse it.
- **`git checkout v0.1.3` fails** — run `git fetch origin` first. If the branch genuinely doesn't exist remotely, the v0.1.3 work hasn't been pushed from Mac yet — stop and report.
- **`Could not read <sha>` errors during git operations** — the `.git/`-via-Dropbox corruption pattern. Re-run step 2 after a minute (Dropbox sync catching up). Persistent errors mean the local `.git/` is genuinely corrupt — see `releases/RECOVERY.md` for the fresh-clone path.
